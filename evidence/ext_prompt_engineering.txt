输出格式：只输出一个 JSON 对象，字段名、字段顺序必须与下方 schema 逐字一致，
          不要输出任何解释文字、不要加 Markdown 代码块围栏。

Schema：
{
  "dataset": "campus_shuttle_app_feedback_2026_04",
  "stakeholder": "app_engineering_team",
  "issues": [
    {
      "id": "R01",
      "reported_date": "YYYY-MM-DD",
      "source_channel": "<受控词汇①>",
      "component": "<受控词汇②>",
      "symptom": "一句话描述观察到的异常现象",
      "observed_behavior": "记录里实际发生了什么",
      "expected_behavior": "记录里期望发生什么，未提及写 null",
      "platform": "操作系统或平台，未提及写 null",
      "app_version": "应用版本，未提及写 null",
      "device": "设备型号，未提及写 null",
      "frequency": "<受控词汇③>",
      "severity_for_engineering": "<受控词汇④>",
      "is_regression": "是否回归问题，未提及写 null",
      "evidence_quote": "原文连续片段",
      "repro_inputs_needed": ["复现或定位还需要哪些信息"],
      "needs_follow_up": true
    }
  ],
  "backlog_hints": {
    "cluster_by_component": {"component名": 条数},
    "blockers": ["id"],
    "highest_debug_value_records": ["id"]
  }
}

受控词汇（只能用下列取值，不得自造新标签）：
  source_channel: 应用评论 | 客服邮件 | 调查反馈 | 聊天记录
  component: eta_prediction | live_tracking | payment_billing | ticketing_qr | notification | ui_accessibility | accessibility_data | location_permissions | localization
  frequency: one_off | intermittent | recurring | reproducible | unknown
  severity_for_engineering: critical | major | minor | enhancement
规则：
1. 每条记录恰好产生一个对象，id 必须保留原始 R 编号，不得合并、不得遗漏、不得新增。
2. evidence_quote 必须是原始记录中的连续原文片段（可截取，不得改写、不得翻译、不得拼接）。
3. 原文未提供的信息一律写 null，不要用猜测填充；复现所需但原文没给的信息写进 repro_inputs_needed。
4. 不得推断技术原因或责任方（例如不得写"服务器故障""GPS 漂移""数据库迁移"）。
5. JSON 必须可被解析：双引号、无注释、无尾随逗号、布尔值不加引号。
6. severity_for_engineering 只看记录本身：涉及金钱损失或人身安全、或功能完全不可用记 critical；主要功能受损但有替代路径记 major；体验瑕疵记 minor；纯新增需求记 enhancement。
7. backlog_hints.blockers 必须是 severity_for_engineering 为 critical 的记录 id；cluster_by_component 的条数必须与 issues 中实际统计一致。
