**日志怎么对应。** `runs/` 下的 `ui_*.json` 里，6 份是报告正文引用的正式运行（基线、A2、四组参数各一份），

## 三、实验概况

| 项目 | 内容 |
|---|---|
| 模型 | `deepseek-v4.1-flash`（接口别名；服务端回报后端为 `deepseek/deepseek-flash`） |
| 调用方式 | 直接调 API：`POST /v1/chat/completions`，请求体显式携带 `temperature` 与 `top_p` |
| 实验平台 | 自建本地网页实验台（`scripts/ui_server.py`），本地服务 + 单页界面 |
| 参数实验 | 四组设置（0.2/0.3、0.7/0.9、1.0/0.95、1.2/1.0）各 1 次，共 4 次 |
| 基线 | P1 提示，T=0.2 / Top-P=0.3，1 次 |
| 评审 | 七维 LLM-as-a-judge，评 5 份（基线 + 四组） |
| 截图 | 6 张，均为手动截取，`temperature` 与 Top-P 与右侧请求参数同屏 |

**为什么自建平台**：DeepSeek 网页对话界面不提供 `temperature` 与 `top_p` 的控制入口。若在对话内重复提问，
四次请求的实际参数完全相同，构不成参数对比。因此改为直接调 API。

**实验怎么做的**：在实验台上依次设定参数与提示词 → 发请求 → 核对回显参数 → 手动截图 → 输出原文落笔记。
四组除参数外其余条件保持不变。可信度不靠叙述，靠日志——每个结论引用的输出都能在 `runs/` 与
`我的实验/outputs/` 里找到原文（日志里的 `sha256(content)` 字段可用于校验，报告本身不再列出哈希）。

## 六、需要注意的三点

1. **每组只跑了一次**，没做重复实验，因此无法分离参数效应与采样噪声。这一点写进了第 9 节。
2. **评审也是模型**。核查发现其事实认定基本可靠，但评分尺度不稳（同类缺陷只对组 3 扣分）。
   第 6.3 节末尾用相同条件复跑一次：总分 ±2 内浮动、首末名互换，而基线与改进版 10 分的差距稳定复现。
   所以四组之间 1–2 分的差距不可靠，基线与改进版 10 分的差距才可信。
3. **`temperature` 的作用未单独分离**。四组是同时调 `temperature` 与 `top_p` 的。第 7.1 节的表述限于
   「在这四组上，`temperature` 从 0.2 升到 1.2 并没有改变输出结构」，未推广为模型特性。
